# Release (Phase 2, documented but not wired up)

> Status: **not wired up yet.** There is no `.goreleaser.yaml` or release workflow yet.
> They are tracked by the OpenSpec change `add-release-and-registry`. Until that change is
> implemented, do not tag or publish anything. Explain this plan to the user and stop.

## Decisions

- **Version source of truth: annotated git tags** `vMAJOR.MINOR.PATCH` (SemVer). There is
  no VERSION file. The binary gets its version at build time via
  `-ldflags "-X main.version={{.Version}}"`. The server reports it in the MCP
  `initialize` response (`serverInfo.version`) and with `--version`.
- **Changelog:** generated by goreleaser from conventional commits since the previous
  tag, grouped into Features (`feat`), Fixes (`fix`), and Other. `docs`, `chore`, `test`
  and `ci` are excluded.
- **Artifacts:** goreleaser builds `linux/amd64` and `linux/arm64` (Raspberry Pi 4 and
  up), `CGO_ENABLED=0`, tar.gz archives and `checksums.txt`.

## Intended procedure (once wired up)

1. `git pull`. CI is green on `main`. No open OpenSpec change for this release is
   un-archived.
2. Run the `publish-guard` skill.
3. Choose the next version from commits since the last tag (`feat` means minor, `fix`
   means patch, `!` or `BREAKING CHANGE` means major).
4. `git tag -a vX.Y.Z -m "vX.Y.Z"`, then push the tag ONLY after the user confirms.
5. The release workflow runs `goreleaser release --clean`. Verify the assets and the
   changelog on the GitHub release page.
6. If published to the MCP registry, bump `server.json` in the same release.
